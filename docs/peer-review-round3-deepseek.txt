--- T3: EIGHT PRIMITIVES ---
3.1 NAC.scope:
ergonomics: acceptable
reason: La API encadenable (root.scope(...).register(...)) es fluida. La restriccion de separador fijo . es aceptable para consistencia, aunque algunos adoptantes pueden preferir otro separador.
edge_case_missed: En nac-v2-extensions.js, _makeSubScope no valida que spec.slug no sea una cadena vacia, solo que no contenga .. Una cadena vacia pasaria la validacion y luego produciria slugs malformados.
perf_concern: Ninguna. La creacion de scopes es O(1) y no toca el DOM.

3.2 NAC.autoRegister:
ergonomics: acceptable
reason: La deteccion automatica de scope ascendente y derivacion heuristica reduce el boilerplate. La opcion i18n_strict controla adecuadamente el rigor.
edge_case_missed: Si un elemento tiene data-nac-action pero el inheritScope falla (sin ancestro data-nac-scope), el slug se deriva como huerfano sin prefijo. El spec no menciona si esto deberia advertirse. En la practica, es facil que ocurra en paginas con multiples regiones dinamicas.
perf_concern: El throttle de 50ms y el limite de 200 llamadas/segundo son adecuados. El MutationObserver con subtree=true en el watch puede ser costoso en DOMs muy grandes; el limite superior mitiga el riesgo.

3.3 NAC.adopt:
ergonomics: acceptable
reason: La interfaz basada en selectores CSS es expresiva. La separacion de reglas (Stripe, Slack) como paquetes independientes es correcta.
edge_case_missed: Si el selector coincide con elementos anadidos despues de observe:true, pero esos elementos estan dentro de un Shadow DOM cerrado, la regla fallara silenciosamente. El spec deberia indicar que adopt no penetra Shadow DOM (eso es tarea de bridgeShadowRoot).
perf_concern: querySelectorAll en cada mutacion sobre document.body puede ser lento. La implementacion en nac-v2-extensions.js ejecuta process para cada nodo anadido que coincida con el selector. Seria mas eficiente usar un solo querySelectorAll sobre el contenedor tras un debounce, en lugar de por nodo.

3.4 NAC.bridgeShadowRoot:
ergonomics: acceptable
reason: La API es simple y explicita.
edge_case_missed: La recursion no verifica si un shadow root ya fue puenteado, pudiendo causar registros duplicados si se llama varias veces sobre el mismo host.
perf_concern: La recursion sobre shadow roots anidados puede disparar autoRegister muchas veces; el limite de profundidad 6 es seguro.

3.5 NAC.bridgeIframe:
ergonomics: problematic
reason: La dependencia de postMessage y la necesidad de que el iframe tambien cargue nac.js limita su adopcion. El handshake asincrono anade latencia y posibles timeouts. Para casos simples (mismo origen) se esperaria un acceso directo al contentWindow.NAC.
edge_case_missed: Si el iframe redirige a otra URL, el handshake fallara, pero no hay reintento. Tampoco se especifica que sucede si el iframe recarga su contenido (nuevo handshake necesario, pero el padre no lo sabe).
perf_concern: El timeout de 5000ms es aceptable.

3.6 NAC.declareVirtual:
ergonomics: good
reason: El patron con slug_pattern y resolver es claro. Cubre un vacio importante.
edge_case_missed: El spec dice que el resolver debe ser idempotente dentro de un describe(), pero la implementacion no lo garantiza. Si el resolver muta estado, dos llamadas a find sobre el mismo slug pueden devolver datos inconsistentes. No se fuerza idempotencia.
perf_concern: El limite de 50ms para el resolver es adecuado, pero la implementacion actual mide el tiempo con performance.now() y emite advertencia; no hay limite estricto (hard fail) a nivel de runtime, solo en el spec.

3.7 NAC.captureEphemeral:
ergonomics: acceptable
reason: La captura en anillo es simple. El acceso mediante describe().ephemeral_log es adecuado.
edge_case_missed: Si un elemento es anadido y eliminado antes de que el MutationObserver se active (debido al throttle), el evento se pierde. La ventana de 3000ms no garantiza la captura de toasts muy rapidos (<100ms). Ademas, el buffer no se persiste entre recargas de pagina, lo que puede ser una limitacion para agentes.
perf_concern: Ninguna, el tamano maximo (~50KB) es minimo.

3.8 NAC.setTenantPrefix:
ergonomics: good
reason: API simple y efectiva.
edge_case_missed: Si se llama despues de que algunos scopes ya se hayan registrado, el prefijo no se aplica retroactivamente, pero el spec prohibe el cambio posterior. El error tenant_prefix_locked es claro.
perf_concern: Ninguna.

--- T4: THREE-PATH IMPERSONATION THREAT MODEL ---
threat_model_completeness: complete
isTrusted_correctness: El uso de event.isTrusted es correcto para la mayoria de los casos. Sin embargo, existen contextos donde isTrusted puede no ser fiable:
- Mobile WebView (Cordova/Capacitor): estos entornos pueden parchear Event.isTrusted o disparar eventos sinteticos que aparecen como isTrusted=true debido a la comunicacion nativa. El spec menciona esto como pregunta abierta, pero no ofrece mitigacion.
- Assistive tech polyfills: herramientas como ciertos emuladores de teclado o lectores de pantalla que inyectan eventos via dispatchEvent tendran isTrusted=false, lo que clasificaria incorrectamente a usuarios legitimos de asistencia como scripts.
- Browser bugs: navegadores antiguos o versiones beta pueden tener bugs donde isTrusted no se establece correctamente para eventos de puntero.
matrix_correctness: La matriz de aplicacion es correcta. La combinacion 'script' + attested=true esta correctamente prohibida. La decision de no requerir attested para 'agent' es acertada, ya que los agentes pueden emitir eventos sin gesto de usuario real.
findings:

id: T4-F1
severity: high
code: istrusted_context_inconsistencies
citation: RFC_v2.0.0.md sec 9.3, spec/NAC-v2.0.md sec 15.10
description: La derivacion de user_gesture_attested desde event.isTrusted es fragil en WebViews, polyfills de asistencia y ciertos navegadores. Usuarios legitimos podrian ser marcados como scripts, bloqueando su acceso. Es necesario un camino de anulacion documentado para herramientas de accesibilidad (por ejemplo, permitir que attestUserGesture sea llamado por extensiones de confianza).
suggested_fix: Anadir un mecanismo de "lista blanca" de origenes de eventos asistivos (configurable por el host) que permita tratar ciertos isTrusted=false como verdaderos. Documentar explicitamente las limitaciones en contextos de WebView y polyfills.

id: T4-F2
severity: medium
code: os_level_agent_signal_ignored
citation: scope doc sec 4b, spec/NAC-v2.0.md sec 15.10
description: La matriz no distingue agentes que operan mediante eventos de SO (Computer Use) de aquellos que usan la API. Un agente OS-level tendra isTrusted=true, pero actualmente no se registra ninguna metadata adicional. Auditorias futuras se beneficiarian de un campo os_level: true en el ProvenanceBlock para distinguir estos casos.
suggested_fix: Anadir un campo opcional os_level en el ProvenanceBlock que la runtime pueda inferir o el agente declarar.

--- T5: I18N CONTRACT (L1) ---
l1_vs_l2_recommendation: keep-l1
default_locale_set: appropriate
catalog_format_gaps:
- El formato de catalogo plano no soporta pluralizacion automatica; depende de sub-claves (ej. key.one). Esto es aceptable para un contrato de formato, pero requiere que los adoptantes definan manualmente cada forma plural. Las bibliotecas de i18n existentes (i18next, FormatJS) manejan esto en runtime; NAC no necesita duplicarlo.
- No hay soporte para formato de fechas/numeros. Es correcto que sea delegado a Intl.

bridge_compatibility:
- react-intl: compatible, mediante un script de build que fusione messages.json por locale en el formato de catalogo NAC.
- vue-i18n: compatible, aplanando los mensajes anidados.
- i18next: compatible, mapeando namespaces a slugs.
- FormatJS: compatible, igual que react-intl.
- gettext (.po): puede requerir un conversor adicional, ya que las claves no son jerarquicas; pero no hay impedimento tecnico.
strict_mode_default: too-aggressive
findings:

id: T5-F1
severity: medium
code: i18n_strict_default_error_nac3
citation: I18N_INTEGRATION_GUIDE.md sec 2.3, spec/NAC-v2.0.md sec 15.11
description: La validacion NAC-3 produce error por defecto cuando falta alguna localizacion. Para SaaS que anaden idiomas incrementalmente, esto romperia el despliegue continuo. La guia sugiere usar NAC-2 mientras tanto, pero muchas organizaciones querran NAC-3 para otros aspectos (seguridad, perf) sin forzar la completitud de i18n.
suggested_fix: El default en NAC-3 deberia ser warn, con opcion a error. Asi se mantiene la visibilidad sin bloquear despliegues. El spec ya sugiere esta opcion en la respuesta al revisor anterior (Grok). Se recomienda implementarla antes del tag.

--- T6: PERF BUDGET REALISM ---
numbers_realistic: Los numeros son realistas en el contexto de sus objetivos. La metrica describe() <30ms para cualquier tamano es agresiva para 10k elementos en moviles de gama baja, pero con paginacion/virtualizacion es alcanzable.
device_trajectory: defensible
hard_fail_thresholds: Las paginas con muchos elementos adopt (muchos selectores complejos) y autoRegister activo pueden superar los limites en moviles de gama baja, especialmente en aplicaciones con listas virtualizadas que ademas usan MutationObserver. El limite de 15ms para adopt por mutacion puede ser excedido si se re-evaluan multiples selectores en un arbol grande.
mutationobserver_throttle: El throttle de 50ms para autoRegister.watch es adecuado para la mayoria de los casos, pero en paginas con 400+ tarjetas y scroll frecuente, 50ms aun puede causar multiples ejecuciones del observer. No se considera un bloqueante.
findings:

id: T6-F1
severity: medium
code: perf_hard_fail_scope
citation: RFC_v2.0.0.md sec 12, spec/NAC-v2.0.md sec 15.13
description: El presupuesto asume que el 5% de las muestras en una ventana de 5 segundos pueden exceder el limite. Esto es estadisticamente laxo: una pagina podria estar funcionando mal durante 250ms cada 5 segundos sin fallar. Para aplicaciones criticas, un umbral de 1% o 1 segundo seria mas apropiado.
suggested_fix: Considerar un umbral mas estricto (1% de muestras en 10s) para NAC-3 en futuras revisiones.

--- T8: CONVERGENCE ASSUMPTION ---
defensibility: weak

adopt_first_class_robustness: La API adopt es de primera clase y permite sobrevivir si el caso D persiste. Sin embargo, la dependencia en selectores CSS y la falta de un mecanismo de "stable ID" mas robusto (como basado en roles ARIA) puede hacer que las reglas sean fragiles ante refactores de los widgets de terceros.
findings:

id: T8-F1
severity: medium
code: convergence_assumption_untested
citation: scope doc sec 6
description: La asuncion de que el mercado presionara a los proveedores a adoptar NAC se basa en la curva de adopcion de ARIA (6 anos), pero NAC es mas complejo y su propuesta de valor para terceros no es tan clara como la accesibilidad legal. Sin datos de early adopters, la suposicion es debil.
suggested_fix: Incluir en el roadmap (fase 5.5 o 6) un esfuerzo proactivo de contacto con al menos 2 proveedores de widgets populares para obtener cartas de intencion o feedback, y asi fortalecer la evidencia.

--- T9: ADOPTION COST ---
greenfield_realistic: optimistic
brownfield_realistic: optimistic
boilerplate_reduction_claim: La reduccion de ~5200 lineas de boilerplate en una app de 200 componentes es posible si el proyecto adopta completamente el nuevo tooling (babel plugin, codemod). Sin embargo, la realidad es que la mayoria de equipos no adoptaran todo el tooling de inmediato. La reduccion real sera gradual.
codemod_40pct_manual_classes: Componentes con logica de negocio compleja (multistep wizards, integraciones de mapas, editores de texto enriquecido) caeran en el 40% manual. Tambien cualquier componente que use renderizado condicional con multiples data-nac-action diferentes.
findings:

id: T9-F1
severity: medium
code: adoption_cost_too_optimistic
citation: scope doc appendix A
description: Las estimaciones de 10h para greenfield y 36h para brownfield asumen un equipo familiarizado con NAC y con el tooling funcionando perfectamente. La realidad de la adopcion temprana incluye tiempo de aprendizaje, depuracion de tooling y ajustes de diseno, facilmente duplicando esas cifras.
suggested_fix: Anadir un factor de "primera adopcion" de 1.5x-2x para los primeros proyectos, y documentar que los costes bajaran con la madurez del ecosistema.

--- T11: AUTHOR OPEN QUESTIONS ---
Q1 (hierarchical scope vs graph): La jerarquia es suficiente para la mayoria de los casos. Un grafo (multiples padres) anadiria complejidad innecesaria. Propongo mantener la jerarquia y reevaluar en v2.1 si aparecen casos de uso reales.

Q4 (convergence assumption): La suposicion es debil (ver T8), pero NAC esta disenado para sobrevivir sin ella gracias a adopt. No es necesario un rediseno, solo transparencia.
Q5 (perf budget): Realista en su mayoria, pero adopt y describe para 10k elementos pueden fallar en gama baja. El margen de fallo (5% de muestras) es demasiado amplio.

Q7 (tooling list): Faltan piezas (ver T7). Deberian anadirse adaptadores de prueba y telemetria antes del lanzamiento.
Q8 (deferral list): La lista es aceptable. Guided task flows y capability negotiation son importantes pero complejos; pueden esperar a v2.1.
Q9 (spec/consumer division): La division es correcta. data-nac-action deberia ser SHOULD en NAC-3, no MUST, para permitir la auto-deteccion como alternativa valida.
Q10 (strict-superset invariant): Se honra. La validacion T2 no encontro rupturas.
Q11 (L1 vs L2): Mantener L1 firmemente. L2 crearia conflictos con las bibliotecas de i18n existentes y sobrecargaria el alcance de NAC. La recomendacion de Sumi es acertada.
