Round 3 cross-compare for findings index. The T4-F1 BLOCKER finding is reproduced here
verbatim because it is critical:]

  - id: T4-F1
    severity: blocker
    code: gesture_buffer_leak_breaks_user_attestation
    citation: js/nac-v2-extensions.js:_captureGestureFromDom (lines ~245-275),
              js/nac-v2-extensions.js:_invoke (lines ~315-325),
              docs/NAC_v20_SCOPE_AND_ECOSYSTEM.md:415-460 (threat model table)
    description:
      The runtime captures `event.isTrusted` from ANY click/keydown/keyup/touchstart/pointerdown
      event on `document` into a single global variable `_lastGestureTrusted` with a 100ms
      freshness window (`GESTURE_FRESH_MS = 100`). When `_invoke` runs to dispatch a NAC
      action, it reads this global without any binding to the specific element being invoked.

      Attack: a malicious script (or compromised browser extension that can emit events into
      the page; or any script claiming `source.type='user'`) waits for a real user to click
      ANYWHERE on the page (filling the buffer with `_lastGestureTrusted=true`), then within
      100ms calls `someScopeNode.register(...).invoke({source:'user'})` on a totally unrelated
      element. The invoke()'s attestation read returns the leaked `true`, the matrix accepts
      the event, the action fires.

      This is the FOURTH impersonation path that scope doc 4b does not cover. The threat model
      table claims "user impersonation: code emits type='user' to bypass HMAC requirement"
      becomes "rejected (user_gesture_attested=false -> contradiction)". Per the rc2 runtime,
      the contradiction does not occur during the 100ms window after any user gesture, so the
      defence is bypassable any time the user is interacting with the page (which is most of
      the time on an active session).

      The cost-of-attack assertion in scope doc 4b ("requires kernel access or browser
      exploit") is wrong for the rc2 implementation. Cost-of-attack is "any script that can
      time itself within 100ms of a user gesture", which is trivial.

      This is BLOCKER-severity for the same reason the v1.9 closing arbiter (Claude) called
      mandatory HMAC critical-path: an audit pipeline that accepts `source.type='user' +
      attested=true` based on gesture-buffer leak is back to where it started.
    suggested_fix:
      Bind the captured `isTrusted` to the specific event target (or its event-path) -- not to
      a global flag. One implementation: when capturing the gesture, also store
      `_lastGestureTarget = e.target` and walk the composed path; when `_invoke(slug)` runs,
      verify that `entry.element` is in the captured event path before honouring `attested`.
      If the invocation is on an element not in the path, treat `attested=null` (unknown) and
      the matrix rejects.

      Additionally: drop GESTURE_FRESH_MS from 100ms to 16ms (one frame), or require the
      handler chain to be synchronous from the original event (most realistic clicks already
      are; promises that resolve later genuinely should not be considered user-attested).

      This is the same problem CSRF tokens solve at the network layer; the design pattern is
      well-understood. Spec sec 15.10 + scope doc sec 4b need an attack-and-defence walk-through
      mirroring the existing three-path table.
