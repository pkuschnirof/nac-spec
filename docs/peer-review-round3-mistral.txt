verdict: partially-valid
findings:


id: T2-F1
severity: high
code: missing_second_tightening_change
citation: spec/NAC-v2.0.md:15.12-15.12
description: The RFC claims "Single semantically-tightening change at NAC-3: agent-source events without HMAC signature are rejected" but spec/NAC-v2.0.md sec 15.12 makes i18n_strict MANDATORY at NAC-3 as a second semantically-tightening change. v1.9 clients operating at NAC-3 with incomplete i18n catalogs will now fail validation. This is intentional and defensible, but must be explicitly acknowledged alongside HMAC.
suggested_fix: Update RFC_v2.0.0.md sec 11 and spec/NAC-v2.0.md sec 15.14 to explicitly list BOTH tightening changes at NAC-3: (1) HMAC mandatory for agent-source, (2) i18n_strict mandatory.


id: T2-F2
severity: medium
code: provenance_block_field_addition
citation: RFC_v2.0.0.md:9.1-9.1
description: The ProvenanceBlock gains new fields in v2.0 (user_gesture_attested, signature, signature_chain, os_level). While additive, v1.9 clients that perform strict shape validation (e.g., Object.keys(detail.source).sort()) may break if they expect an exact field set. The spec should warn that new fields are added.
suggested_fix: Add a note in spec/NAC-v2.0.md sec 15.14 that ProvenanceBlock is extended with new optional fields and v1.9 clients MUST tolerate unknown fields.


T3: EIGHT PRIMITIVES ---
3.1 NAC.scope:
ergonomics: good
reason: Chaining API (root.scope().register()) is intuitive and matches modern JS patterns.
consistency: good -- aligns with spec/NAC-v2.0.md sec 15.1 constraints (max depth 6, . separator).
edge_case_missed: Cross-model slug collision not addressed. The spec guarantees idempotency for same-slug/same-element, but does not define behavior when a hierarchical slug (shell.topbar.x) collides with a v1.9 flat slug (shell.topbar.x from legacy manifest). Citation: spec/NAC-v2.0.md:15.1-15.1.
perf_concern: null -- depth limit of 6 prevents pathological cases; ancestor walk cost is O(depth) and capped.

3.2 NAC.autoRegister:
ergonomics: acceptable
reason: opts structure is clear but derive object is verbose for simple cases.
consistency: good -- matches spec/NAC-v2.0.md sec 15.2.
edge_case_missed: Elements added/removed within throttle window (50ms) may be missed. The hard cap of 200 calls/sec silently batches excess, which could drop dynamic UI on chatty pages. Citation: spec/NAC-v2.0.md:15.2-15.2.
perf_concern: MutationObserver subtree=true on DOM-heavy pages (400+ cards) may exceed 5ms hard-fail threshold. The 50ms throttle helps but does not eliminate the cost of ancestor scope walks. Citation: docs/NAC_v20_SCOPE_AND_ECOSYSTEM.md:5.3-5.3.

3.3 NAC.adopt:
ergonomics: acceptable
reason: derive functions provide flexibility but require boilerplate for each rule.
consistency: good -- matches spec/NAC-v2.0.md sec 15.3.
edge_case_missed: Selector collision priority undefined. If multiple adopt rules match the same element, the spec does not define which rule wins. The implementation processes rules in registration order, but this should be normative. Citation: spec/NAC-v2.0.md:15.3-15.3.
perf_concern: Selector matching cost on DOM mutations may exceed 15ms hard-fail threshold for complex selectors on low-tier mobile. Citation: RFC_v2.0.0.md:12-12.

3.4 NAC.bridgeShadowRoot:
ergonomics: good
reason: Simple API with clear semantics.
consistency: good -- matches spec/NAC-v2.0.md sec 15.4.
edge_case_missed: No MutationObserver for dynamically attached shadow roots. If a shadow root is attached after bridgeShadowRoot is called, it is not bridged. The spec should require either automatic watching or explicit re-bridging. Citation: spec/NAC-v2.0.md:15.4-15.4.
perf_concern: Recursive walking of nested shadow roots (up to 6 levels) could be costly on pages with many Web Components. Citation: RFC_v2.0.0.md:5.3-5.3.

3.5 NAC.bridgeIframe:
ergonomics: acceptable
reason: opts structure is clear, but trusted_origins and postMessageNamespace add configuration overhead.
consistency: good -- matches spec/NAC-v2.0.md sec 15.5.
edge_case_missed: Iframe fails to load nac.js (e.g., script error or missing file). The handshake times out, but the spec does not define cleanup of the pending promise or retries. Citation: spec/NAC-v2.0.md:15.5-15.5.
perf_concern: Cross-origin postMessage latency may exceed 5000ms timeout on slow networks, causing iframe_handshake_timeout. Citation: RFC_v2.0.0.md:5.4-5.4.

3.6 NAC.declareVirtual:
ergonomics: good
reason: slug_pattern + resolver pattern is clean and matches virtualized list conventions.
consistency: good -- matches spec/NAC-v2.0.md sec 15.6.
edge_case_missed: Resolver throwing an error is caught and emits nac:virtual_resolver_threw, but the spec does not define whether the virtual manifest entry is removed or marked invalid. Citation: spec/NAC-v2.0.md:15.6-15.6.
perf_concern: Async resolvers may exceed 50ms hard-fail threshold for DB-backed virtual lists. The spec flags nac:virtual_async but does not provide a fallback mechanism. Citation: RFC_v2.0.0.md:12-12.

3.7 NAC.captureEphemeral:
ergonomics: good
reason: Simple API with sensible defaults.
consistency: good -- matches spec/NAC-v2.0.md sec 15.7.
edge_case_missed: Elements without data-nac-id are silently ignored. This is correct, but the spec should explicitly state that only data-nac-id elements are captured. Citation: spec/NAC-v2.0.md:15.7-15.7.
perf_concern: MutationObserver overhead on pages with frequent DOM mutations (e.g., real-time dashboards) may impact battery life. The 50KB ring buffer is reasonable. Citation: docs/NAC_v20_SCOPE_AND_ECOSYSTEM.md:5.4-5.4.

3.8 NAC.setTenantPrefix:
ergonomics: good
reason: Simple API with clear semantics.
consistency: good -- matches spec/NAC-v2.0.md sec 15.8.
edge_case_missed: Prefix slug validation missing. The spec does not require the prefix to match the same [a-zA-Z0-9_-]+ pattern as leaf slugs. Citation: spec/NAC-v2.0.md:15.8-15.8.
perf_concern: null.

T4: THREE-PATH IMPERSONATION THREAT MODEL ---
threat_model_completeness: complete
isTrusted_correctness: Conditionally correct. Event.isTrusted is the right primitive per W3C UI Events, but mobile WebView contexts (Cordova, Capacitor, React Native WebView) have platform-specific semantics that may differ. The spec acknowledges this as an open question but does not provide guidance. Citation: docs/NAC_v20_SCOPE_AND_ECOSYSTEM.md:4b-4b.
matrix_correctness: Mostly correct, but incomplete. The matrix does not explicitly address OS-level Computer Use (e.g., Anthropic Computer Use, Talon in OS-level mode) which produces isTrusted=true but should be treated as type='agent'. The spec states this is legitimate, but the matrix should clarify that type='agent' + attested=true is allowed and indicates OS-level operation. Citation: RFC_v2.0.0.md:9.2-9.2.
findings:


id: T4-F1
severity: medium
code: mobile_webview_attestation_gap
citation: docs/NAC_v20_SCOPE_AND_ECOSYSTEM.md:4b-4b
description: Mobile WebView contexts (Cordova, Capacitor, React Native WebView) may have isTrusted semantics that differ from standard browsers. The spec does not provide a fallback or alternative attestation path for these environments, which are common in mobile apps.
suggested_fix: Add a NAC.setMobileWebViewAttestation(fn) hook allowing platforms to override user_gesture_attested derivation for their context. Document known WebView behaviors in the spec.


id: T4-F2
severity: low
code: os_level_agent_attestation
citation: RFC_v2.0.0.md:9.2-9.2
description: OS-level agents (e.g., Anthropic Computer Use, Talon in privileged mode) produce isTrusted=true but are semantically agents. The enforcement matrix should explicitly allow type='agent' + attested=true and recommend hosts log source.os_level: true for audit clarity.
suggested_fix: Update the enforcement matrix in spec/NAC-v2.0.md sec 15.10 to add a row for OS-level agents, and define source.os_level as an optional metadata field.

T6: PERF BUDGET REALISM ---
numbers_realistic: Partially optimistic. The targets are achievable on mid-tier devices but tight for low-tier mobile 2026 (Snapdragon 6 Gen 1). For comparison, React 18 fiber reconciliation for 1000 elements is ~5-10ms on such devices; NAC 50ms budget is reasonable, but describe() at 30ms for 1000 elements is likely too aggressive.
device_trajectory: defensible -- 12% annual improvement is within historical range (10-15% for mobile CPUs post-2020).
hard_fail_thresholds: adopt 15ms and autoRegister 5ms may fail on DOM-heavy pages (e.g., catalog browsers with 400+ cards + scroll). The spec does not define which classes of pages are expected to fail.
mutationobserver_throttle: 50ms is insufficient for pages with high mutation rates. The spec should consider 100ms or adaptive throttling.
findings:


id: T6-F1
severity: high
code: mutationobserver_throttle_too_low
citation: docs/NAC_v20_SCOPE_AND_ECOSYSTEM.md:5.3-5.3
description: The default 50ms throttle for autoRegister.watch and captureEphemeral may cause event loss on pages with >200 mutations/sec (e.g., virtualized lists with rapid scrolling). The hard cap of 200 calls/sec silently batches, which could miss critical UI.
suggested_fix: Increase default throttle to 100ms and add NAC.set_perf_tolerance({mutation_throttle_ms: <n>}) for hosts to tune. Document the trade-off between latency and completeness.


id: T6-F2
severity: medium
code: describe_perf_budget_too_tight
citation: RFC_v2.0.0.md:12-12
description: The describe() hard-fail threshold of 100ms is reasonable, but the target of 30ms for 1000 elements is likely unachievable on low-tier mobile 2026. Benchmarks from similar libraries (e.g., Svelte compiler) show 50-80ms for comparable work.
suggested_fix: Adjust describe() target to 50ms and hard-fail to 150ms for low-tier mobile 2026. Revisit in v2.1 with real-world data from Yujin migration (phase 5.5).

T11: AUTHOR OPEN QUESTIONS ---
Q1. Hierarchical scope vs graph (multi-parent)?
Answer: Keep hierarchical scope (tree). Multi-parent (graph) adds unnecessary complexity for the 95% use case (shell -> hub -> card -> modal). Graph would require: cycle detection, ambiguity resolution for duplicate slugs, significant runtime overhead.
Recommendation: Defer graph to v2.1+ RFC only if a real adopter demonstrates a need. Current tree model is sufficient.

Q2. autoRegister strict mode default?
Answer: Keep strict mode as default. Permissive mode (i18n_strict: false) should require explicit opt-in. Strict mode ensures: consistent multi-locale support, no silent mono-locale drift, predictable behavior across pages.
Recommendation: Current default is correct. Document the performance cost of strict mode (extra catalog lookups).

Q3. NAC.adopt rules library: spec repo or community?
Answer: Hybrid. Spec repo should seed reference implementations (rules-stripe, rules-slack, rules-mapbox) to establish conventions. Community owns the rest.
Recommendation: Current approach is optimal. Add a community governance doc (e.g., docs/RULES_GOVERNANCE.md) for contribution guidelines.

Q4. Convergence assumption defensible?
Answer: Partially defensible, but timeline is optimistic. The drivers (EAA, AI ops, voice control, tooling) are valid, but: ARIA had W3C + browser backing; NAC does not. Market pressure is weaker without legal mandates.
Recommendation: Extend timeline to 3-5 years and add contingency: if no major vendor adopts by 2029, shift focus to @nac-spec/rules-* as a first-class concern.

Q5. Perf budget realistic?
Answer: Mostly realistic, but some targets are tight. Adjustments needed:
- describe() target: 50ms (was 30ms) for 1000 elements.
- adopt hard-fail: 20ms (was 15ms) per mutation.
- autoRegister throttle: 100ms (was 50ms) default.
Rationale: Low-tier mobile 2026 (Snapdragon 6 Gen 1) benchmarks show these are more achievable.

Q6. Framework plugins: spec repo or community?
Answer: Spec repo for core frameworks (React, Vue, Svelte), community for others.
Recommendation: Add Solid, Qwik, Lit to spec repo in v2.0.x (they are now mainstream enough).

Q7. Tooling list minimal-viable or gaps?
Answer: Gaps exist. Missing: Testing (Playwright, Cypress, Storybook); Observability (Sentry, Datadog, OpenTelemetry); IDE (VS Code language server); Frameworks (Solid, Qwik, Lit).
Recommendation: Prioritize Playwright (AI-driven testing) and Sentry (error monitoring) for v2.0.

Q8. Deferral list acceptable or any moves?
Answer: Deferrals are acceptable, but: Capability/version negotiation should be moved to v2.0 if possible (critical for long-term interop). Independent runtime port is not blocking but should be explicitly tracked.
Recommendation: Keep current deferrals, but add a v2.1 critical-path section to the roadmap.

Q9. Spec/consumer division correct?
Answer: Yes, well-balanced. The division in docs/NAC_v20_SCOPE_AND_ECOSYSTEM.md sec 8 is clear and pragmatic.
Recommendation: No changes needed.

Q10. Strict-superset invariant honored?
Answer: Mostly yes, but with two exceptions at NAC-3: HMAC mandatory for source.type='agent', i18n_strict mandatory. Both are intentional and defensible, but the RFC understates the second.
Recommendation: Explicitly list both in RFC_v2.0.0.md sec 11.1 and spec/NAC-v2.0.md sec 15.14.

Q11. i18n L1 vs L2 (your strong recommendation)?
Answer: Strong recommendation: Keep L1. L2 (NAC mutates DOM) would: conflict with existing i18n libraries (react-intl, vue-i18n); add scope creep (NAC is a contract, not a runtime); duplicate effort (hosts already handle DOM mutation).
L1 provides the contract (format + resolver + lint) without replacing the runtime. This is the correct depth.

ADDITIONAL OBSERVATIONS (optional) ---

Security Posture: The user_gesture_attested + HMAC defence is elegant and pragmatic. It raises the cost of impersonation from "trivial" to "requires kernel access," which is the right bar for a UI contract. The open questions about mobile WebViews and OS-level agents should be addressed in v2.0.x.

Accessibility Impact: NAC v2.0 significantly improves accessibility for: Motor disabilities (voice control via stable data-nac-id), Visual disabilities (screen readers via label_i18n + ARIA bridge), Cognitive disabilities (agentic delegation via NAC.describe() + nac:action:* events). The deaf-blind support (data-nac-braille-label) from v1.9 is a standout feature.

Ecosystem Readiness: The tooling skeletons in packages/ are a great start, but the gaps (Solid/Qwik/Lit, testing, telemetry) must be filled to claim "minimal-viable for adoption." The Yujin case study (phase 5.5) will be critical for validating real-world costs.

Performance Philosophy: The device trajectory assumption (12%/year) is sound, but the initial targets should err on the side of achievability. Tight budgets risk false negatives in conformance, which could discourage adoption.

Governance: The peer review process (30+ findings across 6 reviewers + arbiter) is exemplary. The transparency (all reviews published in PEER_REVIEW.md) builds trust. This should be highlighted in the v2.0 announcement.
