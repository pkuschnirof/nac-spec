  ### Before you start: who this is actually for

  NAC is described in technical terms (HTML attributes, JSON
  manifest, JavaScript runtime, event contract). That framing
  is correct but incomplete. The downstream beneficiary of
  every NAC primitive is, more often than not, a human with a
  disability whose access to the UI depends on assistive
  technology that NEEDS a stable, machine-readable contract:

  - People with motor disabilities (limited dexterity, tremor,
    paralysis, RSI) who operate UIs through voice control
    software (Talon, Voice Access, Dragon, browser voice modes).
    Their tools collapse on UIs without stable semantic IDs.
    NAC's data-nac-id + label_i18n is exactly that contract.
  - People with visual disabilities (blindness, low vision,
    dyschromatopsia) whose screen readers consume ARIA but
    benefit from NAC.describe()'s richer manifest-grade
    introspection.
  - People with cognitive disabilities, chronic illness, ADHD,
    executive-function variation, autism spectrum, who delegate
    multi-step UI work to AI assistants when they cannot
    navigate alone. NAC's agentic loop pattern (sec 9.1, 9.2)
    makes that delegation auditable.
  - People whose capabilities vary day-to-day (chronic pain,
    medication side effects, mental health). On a hard day,
    the same person who navigates fluently on a good day can
    delegate the work and not lose access to the system.

  The cost of a sloppy contract is not a CI failure. It is a
  user locked out of a system they need.

  This round, the spec adds a new section to PHILOSOPHY.md
  titled "What NAC does for people with disabilities" that
  develops the above. **Please read it before you start your
  review** -- the technical evaluation that follows means more
  when you carry the stakes. Treat the engineering critique as
  seriously as you would for any other spec, and add a layer
  that asks: does this contract actually deliver on the
  promise to those humans?

Its primary audience is frontend teams and assistive‑technology/automation authors; the downstream beneficiaries are people with motor, visual, and cognitive disabilities who depend on stable semantic IDs and auditable agentic loops. v1.7.0 ships canonical event‑detail shapes (sec 6.2), a strict‑superset migration path for legacy fields, a runtime drag/drop primitive, role‑aware click success events, a section‑visibility highlight, 11 new widget demos, and an executable “v1.7 event conformance” self‑test.

T2. Architectural review (200–400 words)
Strongest design decision. Section 6.2’s move to per‑family canonical event detail shapes (explicit TypeScript‑style interfaces and entity‑specific id fields such as field_id, tab_id, stepper_id, etc.) is the most consequential design win. Technical Review: NAC v1.7.0 (Native Accessibility Contract)
T1. SUMMARY (under 120 words)
NAC proposes a machine-readable contract for web UI accessibility: HTML data-nac-* attributes plus a JSON manifest, enforced by a JavaScript runtime that emits canonical events and validates ARIA consistency. The primary audience is developers building accessible interfaces; downstream beneficiaries are people with motor, visual, and cognitive disabilities who depend on assistive technology or AI delegation. As of v1.7.0, NAC ships per-family canonical event detail shapes (sec 6.2), role-aware NAC.click, a drag_drop primitive, ARIA state-mismatch hard errors, an executable self-test suite, and 11 new widget demos covering the full event surface.

T2. ARCHITECTURAL REVIEW (200-400 words)
Strongest design decision in v1.7.0: Section 6.2's per-family entity IDs (action_id, field_id, tab_id, etc.) replace the ambiguous nac_id. This directly addresses the v1.6 review finding that validation was reactive rather than preventive. Now an event consumer can assert event.detail.option_id exists without guessing which generic field contains the identifier. The compile-time contract shift (TypeScript-style interfaces) makes automation predictable — a voice command "select Berlin" maps deterministically to nac:field:changed with option_id.

Weakest design decision: The legacy alias migration plan (accepting both old and new fields with a warning until v2.0) creates a dual-writes tax that will persist in production for teams that defer cleanup. Worse, spec section 6.2 says "the runtime MUST emit both the canonical and legacy fields" but does not specify emission order or warning deduplication. A page with 200 interactive elements could fire 400 events on a single user action, each with duplicate payloads. The legacy_event_field warning also lacks a suppression mechanism for CI pipelines that cannot tolerate console noise during migration.

Section most likely to face friction in production: Section 7.3.2 (NAC-3 hard-error on ARIA/nac state mismatch). While admirable in principle, the gate assumes that ARIA state and NAC manifest state can be kept in sync atomically. In real single-page apps with third-party widget libraries, a date picker might update aria-expanded internally before NAC's mutation observer reacts, causing a transient NAC-3 failure that blocks builds but is invisible to users. The spec does not provide a debounce or reconciliation grace window.

The v1.6.1–1.6.6 patches are solid incremental improvements — particularly the detached-element matcher fix (1.6.4) and role-aware click (1.6.3) — but they don't address the fundamental architectural tension: NAC is a validator AND a runtime, and those roles conflict when strictness breaks real UIs.

T4. RELATIONSHIP TO ARIA + ACCESSIBILITY (≈220 words)
v1.6.1's promotion of aria/nac drift to hard NAC-3 error (sec 7.3.2) + NAC-drives-ARIA-mirrors (7.3.1) + sec 6.2 canonical shapes makes the dual-layer story far more operationally workable. In an enterprise tool serving motor + cognitive users, NAC now reduces net discipline tax over time: once the rendering pipeline enforces atomic updates and the validator runs in CI, teams get both screen-reader compatibility and stable agent/voice contracts "for free" from the same markup. The directionality rule eliminates guesswork.
Limitations remain: ARIA lag in complex SPAs, closed shadow roots out-of-scope, and the per-element attribute tax. Overall, v1.7.0 amplifies value more than cost for teams already invested in accessibility; it turns NAC into a force-multiplier rather than parallel compliance theater.
T5. ADOPTION ANALYSIS (≈200 words)
Minimum work for NAC-3: 5 attributes per interactive element + manifest registration + lifecycle events + validator in CI. AI coding agents make this tractable (minutes per screen per the philosophy).
Most underestimated: Maintaining dual NAC/ARIA state atomically and emitting all required per-family events consistently across dynamic widgets.
Abandonment causes: Validator noise early on, perceived bloat in small apps, or teams hitting the hard ARIA drift gate without pipeline fixes.
vs v1.6.0: Sec 6.2 + dual-emit migration path makes adoption easier. Canonical shapes give implementers clear targets; legacy support lowers the breaking-change risk. The self-test provides immediate feedback, reducing the "does this even work?" uncertainty that kills early pilots. Marginal cost down, confidence up.
