NAC v2.0.0-rc1 -- Round 3 Independent Peer Review
Prompt for: DeepSeek (Pensamiento Profundo) | ChatGPT | Mistral

You are reviewing the release candidate of NAC v2.0.0 (Native
Accessibility Contract). NAC is a public design norm and reference
runtime that lets AI agents, voice assistants, RPA bots and
automated test runners operate any UI as if they were human users.

Two prior review rounds (v1.7 -> v1.8 in April 2026; v1.8 -> v1.9
in May 2026) closed 30+ action items across the same panel. The
v1.9 closing arbiter (Claude) issued a "Conditional YES" verdict
with one critical-path item deferred: HMAC mandatory at NAC-3.

This Round 3 reviews v2.0.0-rc1, which:
  - Promotes the deferred HMAC item from optional to mandatory at
    NAC-3.
  - Adds eight composition primitives (scope, autoRegister, adopt,
    bridgeShadowRoot, bridgeIframe, declareVirtual, captureEphemeral,
    setTenantPrefix).
  - Closes a NEW threat the spec author surfaced after v1.9
    closing: user/script impersonation (declaring source.type='user'
    to bypass HMAC). Closed via `user_gesture_attested` field
    derived from DOM Event.isTrusted.
  - Introduces an i18n contract layer (L1: format + resolver +
    lint, NO DOM mutation) that does not replace existing i18n
    libraries.
  - Ships tooling skeletons (babel/vue/svelte plugins, devtools,
    codemod, cookbook, rules-stripe/-slack/-mapbox).

The author is asking the panel to validate v2.0 along the
implementation/adoption axis the v1.7 -> v1.9 rounds did NOT cover.
The Claude arbiter scored adoption ease 6/10 in v1.9 closing pass --
this round is the diagnosis of that score.

THE 12 TASKS
----------------------------------------------------------------

T1. DOCUMENT ACQUISITION CONFIRMATION

  For each of the 14 required documents, confirm "READ FULLY",
  "READ PARTIALLY (state which sections)", or "COULD NOT FETCH
  (state reason)". Documents not READ FULLY automatically
  downgrade your verdict ceiling.

T2. STRICT SUPERSET CLAIM VALIDATION

  RFC_v2.0.0.md sec 11.1 lists every public API in v1.9 vs v2.0.
  Walk the diff and validate the claim "every v1.9 client keeps
  working unchanged at NAC-1 and NAC-2". Find any breaking change
  the author missed. Any breaking change at NAC-1 or NAC-2 is a
  BLOCKER finding.

  At NAC-3, the author acknowledges one intentional behaviour
  change (unsigned agent events rejected). Validate that this is
  the ONLY semantically-tightening change.

T3. EIGHT PRIMITIVES INDIVIDUAL EVALUATION

  Evaluate each primitive separately. For each, output:
    - API ergonomics (good / acceptable / problematic + reason).
    - Internal consistency with the rest of the spec.
    - Edge case the author missed (cite line range if you find
      one in the spec).
    - Performance concern (if any) on low-tier mobile 2026.

  The 8 primitives:
    3.1  NAC.scope(spec)               -- hierarchical constructor
    3.2  NAC.autoRegister(el, opts)    -- DOM-driven registration
    3.3  NAC.adopt(rule)               -- third-party non-compliant
    3.4  NAC.bridgeShadowRoot(host)    -- Shadow DOM
    3.5  NAC.bridgeIframe(iframeEl, opts) -- same-vendor iframes
    3.6  NAC.declareVirtual(spec)      -- virtualized lists
    3.7  NAC.captureEphemeral(opts)    -- transient UI
    3.8  NAC.setTenantPrefix(slug)     -- multi-tenant naming

T4. THREE-PATH IMPERSONATION THREAT MODEL

  scope doc section 4b describes three impersonation paths (forged
  agent, user impersonation, script-claiming-user) and the v2.0
  defence (HMAC mandatory + user_gesture_attested + matrix at
  NAC-3).

  Validate:
    - Is the threat model complete? Is there a fourth impersonation
      the author missed?
    - Is `event.isTrusted` truly the right primitive, or are there
      browser bugs / Shadow DOM edge cases / mobile WebView
      contexts where it lies?
    - Is the enforcement matrix at NAC-3 correct, or are there
      legitimate use cases (e.g. assistive tech, OS-level
      Computer Use) that the matrix incorrectly rejects?

T5. I18N CONTRACT (L1) VALIDATION

  Read I18N_INTEGRATION_GUIDE.md FULLY. The author chose L1
  (format + resolver + lint, no DOM mutation) over L2 (full
  runtime). Validate this choice:
    - Is L1 the right depth, or should NAC v2.0 push to L2?
    - Is the 10-locale default the right starting set, or should
      NAC ship a smaller (5-7) or larger (15+) default?
    - Does the catalog format support every common i18n pattern
      typical adopters need (plurals, gender, grammatical cases,
      interpolation, RTL/BIDI, CJK widths)? Cite gaps.
    - Can react-intl / vue-i18n / FormatJS / i18next / gettext
      bridges cleanly to this format? Find one bridge that breaks
      if such exists.
    - Is strict mode at NAC-3 (error on missing locale) too
      aggressive for typical SaaS rollouts where new languages
      are added incrementally?

T6. PERFORMANCE BUDGET REALISM

  scope doc section 5 + RFC sec 12 + spec sec 15.13 quote a perf
  budget targeting low-tier mobile 2026. Validate:
    - Are the numbers realistic? (If you have benchmark intuition
      from comparable libraries, cite them.)
    - The "device trajectory 2026 -> 2030" assumption (12% per
      year compounding) -- is this defensible or optimistic?
    - The hard-fail thresholds (e.g. autoRegister 5ms, adopt 15ms)
      -- on which class of pages do they realistically fail?
    - The MutationObserver `subtree=true` cost on DOM-heavy pages
      (catalog browser with 400 cards + scroll) -- is the throttle
      50ms enough?

T7. TOOLING ECOSYSTEM COMPLETENESS

  scope doc section 7 + roadmap phase 4 list 9 packages. Validate:
    - Is the list minimal-viable for "v2.0 is adoptable", or is
      something missing? Specifically:
        * What about Solid / Qwik / Lit support?
        * What about Storybook / Playwright / Cypress integrations?
        * What about Sentry / Datadog / OpenTelemetry telemetry
          export?
        * What about a Visual Studio Code language server for
          NAC manifest schema validation?
    - Should @nac-spec/rules-* be in the spec repo or a separate
      community-curated repo? The author chose: spec repo seedes
      Stripe/Slack/Mapbox, community owns rest. Validate.
    - Is the codemod auto-coverage target (~60%) realistic for
      typical brownfield React/Vue/Svelte codebases? Higher? Lower?

T8. CONVERGENCE ASSUMPTION DEFENSIBILITY

  scope doc section 6 and migrator analysis section 7 assume that
  third-party widget vendors will adopt NAC compliance under
  market pressure within 2-4 years (driven by EAA, AI ops,
  voice control resurgence, tooling-cheap adoption).

  Validate:
    - Is this assumption defensible based on the WAI-ARIA adoption
      curve (2012 minority -> 2018 universal in design systems)?
    - What single event would falsify the convergence (e.g. if it
      does NOT happen by month X, NAC must restructure how)?
    - Is `NAC.adopt` first-class (not relegated to "transitional")
      enough to survive case D structural permanence?

T9. ADOPTION COST VALIDATION (greenfield + brownfield)

  scope doc appendix A + section 9 quote:
    - Greenfield app of 50 components + 10 modals: ~10h dev.
    - Brownfield Yujin (~50 components, partial i18n + ARIA):
      ~36h dev including codemod + manual cleanup + i18n gap fill.

  Validate:
    - Are these realistic for a typical React/Vue team adopting
      NAC v2.0 with the SDK?
    - Specifically: the "5200 lines of boilerplate eliminated"
      claim in appendix A -- realistic, optimistic, or
      pessimistic?
    - The codemod auto-coverage 60% target -- what classes of
      components fall in the 40% manual cleanup?
